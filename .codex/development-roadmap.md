# Kontiki 開発ロードマップ

## 目的

Kontiki を、既存サイトを壊さずに育てられる、ポータブルで安全かつ操作しやすい
CMS にする。

開発では、新機能を早く追加することだけでなく、現在動いているサイトを継続して
動かせることを重視する。この「既存サイトを介護しながら改善する」という姿勢を、
すべての設計・移行・リリース判断の前提とする。

パッケージ統合とインストール方式の基本方針は
[v1-architecture.md](v1-architecture.md) を参照する。

## 長期目標

1. 既存サイトを壊さない
2. 堅牢な実装と CSP を含む、セキュリティ不安の少ない CMS にする
3. 管理画面をキーボードや支援技術でも操作できる状態に保つ
4. 安定して動作させ、特にファイルアップロードのモーダルを改善する
5. SQLite と相対的なパス設計により、フォルダ単位で移動できるようにする
6. model の定義から、多様な入力欄・検証・保存処理を生成できるようにする
7. Kontiki の前身 CMS から安全に移行できるようにする
8. 公開コンテンツから静的サイトを生成できるようにする

Markdown の採用はコンテンツ作成上のアクセシビリティを支えるが、それだけで
見出し構造、代替テキスト、リンク文言などが保証されるわけではない。編集 UI と
出力結果の双方を確認対象とする。

## 開発中に守る不変条件

- v0.9 系の保守は保守ブランチで行い、v1 開発と混ぜない
- 公開済みタグと公開済みマイグレーションの内容を変更しない
- `composer update` だけで DB マイグレーションを実行しない
- サイト所有の設定、DB、コンテンツ、アップロードファイルを上書きしない
- 本番データや認証情報をリポジトリに保存しない
- 原則として、リファクタリングと仕様変更を別のコミットにする
- コンテンツ種別や model ごとのアドホックなテーブル増設を前提にしない
- clean install と既存サイトからの update の双方をリリース判定に使う
- 破壊的な移行は、バックアップ、照合、復旧方法が揃うまで行わない

## DB 設計と移行の方針

既存 DB の構造は互換性のために永久保存する対象ではない。可用性や保守性に問題が
ある場合は、既存サイトに影響を出さない段階的な移行を用意したうえで、正規の構造を
改善する。

ただし、調査前に EAV や単一 metadata カラムなどの方式を決め打ちしない。まず既存の
スキーマ、クエリ、model、保存値、検索・並べ替え・一意性の要件を確認し、その結果を
設計判断として記録する。

目指す性質は次のとおり。

- CMS 全体で共有できる、少数で安定した正規スキーマを持つ
- model は物理テーブルではなく、保存用のインターフェースに依存する
- CMS 共通の属性と、model 固有フィールドの責務を分ける
- model を追加するたびにテーブル作成や `ALTER TABLE` を要求しない
- 検索、並べ替え、一意性、型の扱いを明示できる
- clean install と既存 DB の移行後が、同じ正規スキーマへ収束する

DB 再設計は以下の順で行う。

1. 現行スキーマ、全マイグレーション、主要クエリ、実データ形状を棚卸しする
2. 現行動作を固定する特性テストを追加する
3. 正規スキーマと保存境界を ADR として記録する
4. 既存構造を残したまま、新構造を追加するマイグレーションを作る
5. トランザクション内でデータをコピーする
6. 件数、識別子、状態、日時、関連、一意性を照合する
7. `PRAGMA integrity_check` と外部キー違反を確認する
8. repository 層で旧構造との互換期間を設ける
9. clean install と既存サイト複製の双方で切替を検証する
10. 旧構造の削除は、別の明示的な将来リリースまで延期する

公開済みのマイグレーションは書き換えず、修正は新しいマイグレーションとして追加する。

## 段階的な実施計画

### Phase 0: v1 の基準線

現状の基準線。`jidaikobo/kontiki` への統合、明示的な install コマンド、status、
migrate、clean install、v0.9 からの更新シナリオを維持する。

- `v1.0.0-alpha.1` は公開済みの不変な基準点とする
- 失敗した installer の途中生成物を安全に戻す修正は次の候補に含める
- `kontiki-dev` の clean install と update シナリオを回帰確認に使う

### Phase 1: 現行動作の固定

リファクタリングに先立ち、壊したくない動作をテストと確認手順にする。

- 記事の作成、編集、プレビュー、ログインの特性テスト
- DB の読み書き、model 解決、テンプレート解決の特性テスト
- ファイル選択・アップロード・削除・キャンセルの現状調査
- clean install と v0.9 更新後の代表的な HTTP 動作確認
- DB のスナップショット比較と整合性確認

### Phase 2: DB と永続化境界の整理

- 現行 DB と model の利用実態を読み取り専用で調査する
- 正規スキーマ、型、索引、一意性、関連の設計を決める
- controller や model から SQL を隔離する repository 境界を作る
- 追加型マイグレーションと検証可能なデータ移行を用意する

### Phase 3: 動作を変えないリファクタリング

- Bootstrap、設定読込、DI、routing、view 解決の責務を分離する
- 大きな controller と trait を、小さくテスト可能な単位へ分ける
- グローバル状態、暗黙のパス、環境依存処理を減らす
- PSR-4、PSR-12 と明確な型・例外境界へ段階的に寄せる

各変更は小さく保ち、Phase 1 の特性テストが通ることを完了条件とする。

### Phase 4: セキュリティ基盤

- 認証、セッション、CSRF、権限確認を再点検する
- アップロードの MIME、拡張子、保存名、配置先、サイズを検証する
- 出力エスケープと Markdown から生成される HTML の境界を確認する
- CSP は Report-Only で違反を把握してから段階的に強制する
- セキュリティヘッダーと依存パッケージ監査をリリース判定に含める

### Phase 5: ファイル管理 UI の安定化

- アップロード処理とモーダル UI の責務を分離する
- 非同期処理の成功、失敗、中断、再試行を明確にする
- フォーカス移動、フォーカストラップ、閉じた後の復帰を保証する
- 状態通知を支援技術へ伝え、キーボードだけで操作できるようにする
- 二重送信、競合、途中失敗に対する回帰テストを追加する

### Phase 6: model 駆動の編集画面

- model のフィールド定義から入力 UI、検証、正規化、保存を生成する
- label、説明、必須、型、既定値、選択肢、エラーの仕様を統一する
- 検索、並べ替え、一意性をフィールド定義で明示できるようにする
- model 追加だけでは DB マイグレーションを要求しない構造を目指す
- 生成された UI の label 関連付け、エラー通知、フォーカス順を検証する

### Phase 7: ポータビリティの保証

- 絶対パスやホスト固有情報への依存を洗い出す
- サイトディレクトリを複製・移動して起動する自動シナリオを作る
- DB、アップロード、設定、キャッシュの所有境界を明確にする
- CLI の診断コマンドで不足拡張、権限、パス、DB 状態を確認可能にする

### Phase 8: 前身 CMS からの移行

- 前身 CMS のデータ形式と URL 規則を調査する
- 読み取り専用かつ再実行可能な importer を作る
- 件数、本文、添付、日時、公開状態、URL 対応を照合する
- 変換不能データを黙って捨てず、レポートとして残す

### Phase 9: 静的サイト生成

- 公開対象の選択、URL、テンプレート、アセットの契約を定義する
- 下書きや非公開情報が出力されないことを保証する
- 一時ディレクトリへ生成し、成功後に切り替える
- 差分確認と再現可能な build コマンドを用意する

### Phase 10: v1 安定版への成熟

- alpha では設計・移行方式を検証する
- beta では主要仕様を固定し、既存サイト移行を重点検証する
- RC では修正範囲を回帰不具合と文書不足に絞る
- stable は clean install、v0.9 更新、移動、復旧をすべて通してから公開する

`alpha.2` の公開時期は固定せず、十分な変更と検証がまとまった段階で判断する。

## 各段階に共通する完了条件

- 自動テストと静的解析が通る
- `composer audit` で既知の問題を確認する
- clean install と既存サイト複製の update が通る
- DB 変更時は整合性、件数、主要フィールド、復旧手順を確認する
- 管理画面変更時はキーボード操作、フォーカス、label、エラー通知を確認する
- セキュリティ境界変更時は失敗系と権限不足のテストを含める
- サイト所有ファイルと package 所有ファイルの境界を侵していない
- 変更理由、未完了事項、次の作業を `.codex/` に記録する

## 直近の実施順

1. 現行 DB スキーマ、マイグレーション、model、SQL の読み取り専用監査
2. DB と記事編集動作の特性テスト追加
3. 正規スキーマと保存境界の ADR 作成
4. Bootstrap 周辺から、小さな動作不変リファクタリングを開始
5. ファイルアップロードとモーダルの状態遷移を棚卸し

## 未決事項

- 正規 DB スキーマの具体形
- model 固有フィールドの型、索引、一意性の表現方法
- 旧 DB 構造の互換期間と削除時期
- 前身 CMS の移行元データと URL 互換の範囲
- 静的生成物の配置、差分更新、公開方法
- v1 の各 prerelease を切る具体的な判定基準
